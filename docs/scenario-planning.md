**wasurenagusaの立ち位置**: Memory MCP は「最も競争が激しいカテゴリの一つ」。しかし「失敗の自動検知 → 原則への自動統合 → セッション注入」の3段階パイプラインを持つ競合は**ゼロ**。

### wasurenagusaの技術的差別化（競合に無い機能）
1. **dont自動検知**: リトライパターン・感情分析による失敗の自動検出
2. **dont原則統合**: LLMが数百件のエントリを5-7原則に圧縮（508件→7原則、788KB→3KB）
3. **自律タスク実行**: task_submitによるCLI subprocess自動実行（24/365）
4. **ゼロ努力運用**: SessionStart/Stop Hookで完全自動化

### MCPプロトコル自体のリスク（2026年3月時点）

2026年3月、「MCPはなぜCLIに負けたのか」（Zenn）等の論考が出現。主な批判：
- MCPのツール定義がトークンを食いすぎる（GitHub MCP: 93ツール=55,000トークン vs CLI: 225トークン、**43倍の差**）
- モデルの推論能力向上でCLI直接操作が可能に → MCPの「モデルにツールを教える」役割が消失
- Anthropic自身がTool Search Toolで「MCPをそのまま使わない方法」を提案

**wasurenagusaへの影響評価:**
- 批判の主対象は**ツール数が多いMCPサーバー**（GitHub: 93ツール等）。wasurenagusaは~10ツールで軽微
- **コア価値（失敗検知→統合→原則化→注入）はMCPに依存していない**。context/analyze/rebuildは既にCLIで動作
- MCPは「会話中にAIが`memory_save`/`search`を呼べる」追加利便性を提供するレイヤー
- **結論: CLI-first + MCP-optionalの二刀流がwasurenagusaの正しいポジショニング**

### wasurenagusaの現状弱点
1. ~~**Gemini API専用**~~: ~~最大の導入障壁~~ → **Genkit導入で解消済み**（Gemini/OpenAI/Anthropic対応）
2. **Claude Code専用**: Hook機構がClaude Code固有
3. **メモリ肥大化**: 長期運用でログが無限成長（83MB logs実績あり）
4. **英語圏認知ゼロ**: 日本語名＋日本語ドキュメント中心

## PART A — 大失敗シナリオ

> 「ブランド毀損・技術的崩壊・コミュニティからの拒絶が起きた場合」

### 大失敗の主因（上位3つ）
1. **Show HNで「また一つメモリツールか」と1-2 pointsでスルー** → 英語圏に永久に届かない
2. **Gemini APIの仕様変更・料金改定で動作不能に** → ユーザーのプロジェクト記憶が突然消失
3. **セキュリティインシデント: Gemini APIにプロジェクトのソースコードが送信されている**ことが発覚し炎上

### 詳細リスク

| # | テーマ | 大失敗シナリオ | 確率 | ダメージ | 対策 | 残存リスク |

### リスク・成功因子サマリー

- **最大リスク**: ~~LLMプロバイダ依存（Gemini専用）~~ → **解消済み**。現在の最大リスクは**MCPプロトコル自体の衰退**と**claude-memの先行優位**

- **プラットフォームリスク**: (1) Anthropic純正メモリ強化 — 「保存」は12ヶ月以内、「統合・原則化」は12ヶ月以上先と予測 (2) **MCPプロトコル自体への批判拡大** — ただしwasurenagusaはCLI-first設計で影響軽微
- **時間窓**: **2026年6月末**がデッドライン。claude-memが類似機能追加まで推定3-6ヶ月
- **勝負の分かれ目**: 英語READMEの質 × ~~LLMプロバイダ対応~~ ✅ × 初回体験 × 発信継続性 × **CLI-first打ち出し**

### GO / NO-GO 判断
