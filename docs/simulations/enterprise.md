# wasurenagusa — エンタープライズ反応シミュレーション
シミュレーション日: 2026-03-04
視点: エンタープライズ（開発チーム、テックリード、CTO、セキュリティ担当）

---

## 前提整理

**プロダクト特性**:
- AI coding agentの失敗自動検知→原則統合→セッション注入のMCP server
- OSS / MIT / npm公開。個人開発（バス係数=1）
- 外部LLM API（Gemini/OpenAI/Anthropic）にデータ送信する設計

**エンタープライズ環境（2026年3月時点）**:
- AI coding agentの企業導入率: 65%（GitHub Copilot, Cursor中心）
- MCP serverの企業導入: セキュリティレビュー必須。承認プロセスに平均2-4週間
- LLMプロバイダ選択: 企業の80%が自社契約のLLMプロバイダを持つ。特定プロバイダ縛りは「即却下」
- セキュリティ要件: ソースコードの外部送信はセキュリティチーム承認必須
- 導入パターン: ボトムアップ（個人→チーム→組織）が85%。トップダウンは15%

## 大失敗シナリオ（セキュリティ懸念で完全ブロック）

### テックリードの評価
> 「wasurenagusa？面白そうだけど…ちょっと待って。Stop Hookで会話全文をGemini APIに送ってる？
> うちのソースコード、Geminiに送られるってこと？
> セキュリティチームに相談するまでもなく、これは無理。」

### セキュリティチームの反応
> - データ送信先: Google Gemini API（サードパーティ）
> - 送信データ: 開発者の会話履歴（ソースコードの断片を含む可能性）
> - データ保持ポリシー: Gemini API Terms（学習に使用しない）→ ただし検証不可
> - **判定: 使用禁止**

### CISO向け報告
> 「外部LLM APIにソースコードの断片が送信される設計。
> 送信内容の制御機構なし。監査ログなし。暗号化はTLS のみ。
> Enterprise readiness score: **2/10**。使用を推奨しません。」

### なぜ大失敗するか
1. **データ送信の透明性不足**: 何を、どこに、どれだけ送るかがREADMEに明記されていない
2. **企業向け機能の欠如**: RBAC、audit log、data residency、SOC2対応、すべてゼロ
3. **バス係数=1**: 個人開発のOSSに業務依存するリスクを企業は取れない
4. Gemini API縛りが企業の既存契約（Azure OpenAI/AWS Bedrock）と衝突

## 失敗シナリオ（個人利用に留まり、チーム導入に至らない）

### 開発者個人の評価
> 「自分のサイドプロジェクトでは使ってる。効果は実感してる。
> でも会社のプロジェクトで使うとなると…セキュリティレビュー通す気力がない。
> そもそもうちのセキュリティチーム、外部LLM APIへのデータ送信は全部NG。」

### テックリードの反応
> 「コンセプトは良い。'AIに反省を教える'は正しいアプローチだと思う。
> でも今の状態では企業導入は無理。最低限必要なのは:
> - LLMプロバイダ選択（うちはAzure OpenAI）
> - 送信データのフィルタリング（ソースコード除外オプション）
> - audit log（誰が何を送ったか追跡可能）
> - 最低限のドキュメント（セキュリティホワイトペーパー）」

### 結果
- 個人の副業/サイドプロジェクトでは使われる
- 企業のメインプロジェクトでは使われない
- 「面白いけど仕事では使えない」層が大多数

### なぜ失敗で終わるか
1. セキュリティレビューの書類がない（ホワイトペーパー、DPA、SOC2等）
2. LLMプロバイダが企業の既存契約と合わない
3. audit logがなく、コンプライアンス要件を満たせない
4. バス係数=1で「このツール明日消えたら困る」リスク

## 成功シナリオ（ボトムアップで小規模チーム導入）

### 導入パターン（ボトムアップ）

**Step 1: 個人利用（1-2ヶ月目）**
> シニアエンジニアAさんが個人的にwasurenagusaを導入。
> 2週間後、自分のAIが明らかに同じミスをしなくなったことを実感。
> チームのSlackで共有: 「これ面白い。AIが学習してる感覚がある」

**Step 2: チーム試用（3-4ヶ月目）**
> Aさんのチーム（5人）がトライアル的に導入。
> 前提: プロジェクトのソースコードが機密性の低いもの（社内ツール等）
> テックリードの承認: 「セキュリティチームには報告するが、社内ツール限定ならOK」

**Step 3: チームの成果（5-6ヶ月目）**
> チーム全体で共有dontファイルが蓄積。
> 「うちのプロジェクト固有の地雷リスト」が自動生成される。
> 新メンバーのオンボーディング時に「まずwasurenagusaの原則リストを読んで」が定着。

### テックリードの評価
> 「6ヶ月使ってみた結果、チームのAI利用品質が明らかに上がった。
> 特に新メンバーのオンボーディングが楽になった。
> AIが最初からプロジェクトの慣習を知っている状態で作業を始められる。
>
> 企業全体への展開にはまだ課題がある（セキュリティ、audit log）が、
> 小規模チームでの価値は証明された。」

### 予測指標
- 企業導入チーム数: 10-30（ほぼ全てボトムアップ）
- 平均チームサイズ: 3-5人
- 用途: 社内ツール、サイドプロジェクト、非機密プロジェクト
- Enterprise readiness score: **5/10**

### なぜ成功するか
1. multi-LLM対応で企業の既存LLM契約に合わせられる
2. 送信データの範囲がドキュメント化され、テックリードが判断可能
3. 「チーム共有dont原則」が新しい価値として認知される
4. ボトムアップ導入パターンがセキュリティレビューのハードルを下げる（社内ツール限定）

## 大成功シナリオ（エンタープライズグレードに進化）

### エンタープライズ機能の追加（想定）
- LLMプロバイダプラグイン（Azure OpenAI / AWS Bedrock / Google Vertex対応）
- 送信データフィルタリング（ソースコード除外、PII検出）
- Audit log（全API呼び出しの記録）
- RBAC（チーム内の権限管理）
- Self-hosted mode（LLM APIを使わないローカル統合モード）

### 導入パターン

**Phase 1: テックスタートアップ（10-50人）**
> CTO直下の技術判断で導入。セキュリティレビューは簡略。
> 「開発チーム全員がwasurenagusaを使う」状態に。
> 全社のdont原則が自動蓄積 → AIの品質が組織レベルで向上。

**Phase 2: 中規模企業（100-500人）**
> テックリードの推薦で段階的導入。
> セキュリティチーム承認済み（ホワイトペーパー + audit log）。
> チームごとに独立したdontスペース + 全社共通の原則。

**Phase 3: 大企業（1,000人+）**
> Hosted API or Self-hosted版で導入。
> 既存のAI governance frameworkに統合。
> 「AI利用ポリシーの自動執行ツール」として位置づけ。

### CTO評価
> 「wasurenagusaの本質的価値は、AIの利用品質を組織レベルで底上げできること。
> 個人の記憶ではなく、組織の知識として蓄積される。
> これはAI governance の観点からも重要。
> AIが『やってはいけないこと』を自動で学習するのは、
> ポリシー違反の防止にもつながる。」

### 予測指標
- 企業導入チーム数: 100+
- Hosted API MRR: $5,000-15,000
- Enterprise readiness score: **8/10**

### なぜ大成功するか
1. 「AI governance」文脈での価値が認知される
2. チーム共有dont原則が「組織的な学習」として企業に刺さる
3. Hosted版/Self-hosted版でセキュリティ要件を満たす
4. 「AI利用ポリシーの自動執行」という新しい価値提案

## エンタープライズ導入の構造的課題

### 現状のEnterprise Readiness Score: 3/10

| カテゴリ | 現状 | 必要 | ギャップ |
|---------|------|------|---------|
| LLMプロバイダ | Gemini専用 | マルチ（Azure/Bedrock/Vertex） | **Critical** |
| セキュリティ | READMEのみ | ホワイトペーパー + DPA | High |
| 監査 | なし | Audit log + data lineage | High |
| アクセス制御 | なし | RBAC + SSO | Medium |
| デプロイメント | npm install | Self-hosted / Hosted API | Medium |
| サポート | GitHub Issue | SLA付きサポート | Low（Phase 2以降） |
| コンプライアンス | なし | SOC2 Type II / GDPR | Low（Phase 3以降） |

### 推奨ロードマップ

```
Phase 1（〜6ヶ月）: 個人 + 小規模チーム
  - multi-LLM対応
  - 送信データのドキュメント化
  - 基本的なaudit log

Phase 2（6-12ヶ月）: 中規模企業
  - Hosted API
  - RBAC
  - セキュリティホワイトペーパー

Phase 3（12ヶ月+）: 大企業
  - Self-hosted版
  - SSO/SAML
  - SOC2対応
  - 専用サポート
```
