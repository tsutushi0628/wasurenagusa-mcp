## 原則

- ドキュメントが正（ground truth）。まずドキュメントを読み、その記述が正しいかをコードで検証する。
- 事実の修正のみ行う。フォーマット変更、文体の統一、表現の言い換えは一切しない。
- 記述と実態が一致している箇所には触らない。
- 新機能の追記は、既存ドキュメントの構成・粒度に合わせる。大項目を追加する場合は既存セクションとのバランスを保つ。

## 手順

### Phase 1: ドキュメントの全体把握

Steering、Specsの全ドキュメントをReadで読み、以下を把握する:
- 各ドキュメントの構成（セクション一覧）
- 記載されている技術要素（ライブラリ、アーキテクチャ、パターン）
- 記載されている機能・コンポーネント一覧

### Phase 2: 既存記述の正確性を検証

ドキュメントに書かれている各記述について、対応するソースコードをRead/Grep/Globで確認する:
- ファイルパス・ディレクトリ構造は実在するか
- クラス名・関数名・インターフェースは現在のコードと一致するか
- 依存ライブラリのバージョンや名前は package.json と一致するか
- アーキテクチャの説明（レイヤー構成、データフロー）は実装と一致するか
- 「〜を使用」「〜で実装」等の技術的記述は正確か

見つかった乖離をメモしておく。

### Phase 3: 変更ファイルから未記載の新規要素を探す

変更ファイルの内容をReadで確認し、以下を探す:
- ドキュメントに未記載の新しいファイル・モジュール・クラス・関数
- ドキュメントに未記載の新しい依存ライブラリ
- ドキュメントに未記載のアーキテクチャ変更（新レイヤー、新データフロー）
- 既存記述の前提が変わるような構造変更

ドキュメントの粒度から見て記載すべきレベルの変更のみ対象とする。内部実装の軽微な変更は無視する。

### Phase 4: 修正の実行

Phase 2とPhase 3で発見した乖離に対してのみ、Editで修正する:
- 既存記述の誤り → 正しい内容に修正
- 削除された要素 → ドキュメントから削除
- 新規要素 → 適切なセクションに追記

### Phase 5: サマリ出力

更新箇所を以下の形式でまとめる:
```
## 更新サマリ
- [ファイル名]: [変更内容の1行要約]
- [ファイル名]: [変更内容の1行要約]
（更新なしの場合: 「ドキュメントとコードの間に乖離は見つかりませんでした」）
```
