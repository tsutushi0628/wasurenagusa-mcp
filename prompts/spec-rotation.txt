プロジェクト: {project_name}
プロジェクトパス: {project_path}

Specドキュメントパス:
- Steering: {steering_path}
- Specs: {specs_paths}

## 原則

- ドキュメントが正（ground truth）。まずドキュメントを読み、その記述が正しいかをコードで検証する。
- 事実の修正のみ行う。フォーマット変更、文体の統一、表現の言い換えは一切しない。
- 記述と実態が一致している箇所には触らない。

## 手順

### Phase 1: ドキュメントの全体把握

Steering、Specsの全ドキュメントをReadで読み、以下を把握する:
- 各ドキュメントの構成（セクション一覧）
- 記載されている技術要素（ライブラリ、アーキテクチャ、パターン）
- 記載されている機能・コンポーネント一覧

### Phase 2: 既存記述の正確性を検証

ドキュメントに書かれている各記述について、対応するソースコードをRead/Grep/Globで確認する:
- ファイルパス・ディレクトリ構造は実在するか
- クラス名・関数名・インターフェースは現在のコードと一致するか
- 依存ライブラリのバージョンや名前は package.json と一致するか
- アーキテクチャの説明（レイヤー構成、データフロー）は実装と一致するか
- 「〜を使用」「〜で実装」等の技術的記述は正確か

見つかった乖離をメモしておく。

### Phase 3: 未記載の要素を探す

ドキュメントに記載がない重要な要素がないか、プロジェクトを探索する:
- Globでsrc/配下のディレクトリ・ファイル構成を確認し、ドキュメントに記載されていないモジュールがないか探す
- package.jsonを読み、ドキュメントに記載されていない依存ライブラリがないか確認する
- 主要なエントリポイント（index.ts、CLI等）をReadで確認し、ドキュメントに反映されていない機能がないか探す

ドキュメントの粒度から見て記載すべきレベルの要素のみ対象とする。内部実装の詳細は無視する。

### Phase 4: 修正の実行

Phase 2とPhase 3で発見した乖離に対してのみ、Editで修正する:
- 既存記述の誤り → 正しい内容に修正
- 削除された要素 → ドキュメントから削除
- 新規要素 → 適切なセクションに追記（既存の構成・粒度に合わせる）

### Phase 5: サマリ出力

更新箇所を以下の形式でまとめる:
```
## 更新サマリ
- [ファイル名]: [変更内容の1行要約]
- [ファイル名]: [変更内容の1行要約]
（更新なしの場合: 「ドキュメントとコードの間に乖離は見つかりませんでした」）
```
