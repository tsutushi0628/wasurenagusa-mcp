# Requirements Document

## Introduction

wasurenagusa-mcp は、AIコーディングエージェントに永続記憶を与えるMCPサーバである。
本書は、その記憶システムの全面改修（**memory-redesign**）の要件を定義する。

改修の入力は、実運用71日分の操作ログとストア実体に対する読み取り専用監査（`docs/findings/inv-20260703-ux-logic-audit.md`。以下「監査」）と、別途ローカル管理している知識棚卸しとUX実測の記録である。
監査対象のうち最大規模の実運用ストアを、監査と同じく「主ストア」と呼ぶ。

観測された8症状は独立したバグの山ではなく、次の3本の根本原因から派生した系である。

1. push型の全文注入が、確定情報と未確定情報を分離していない。
2. 検索経路の実装細部が誤っている（クエリのトークナイズ、距離尺度、最終順位、project帰属の刻印、削除済みベクトルの蘇生、アーカイブの分断）。
3. 新旧二重系統（v1 Markdown系とv2 SQLite系）が未清算のまま、同じ統合キャッシュを相互に上書きし合っている。

このため本改修は、症状の個別修理ではなく「止血→土台→検索→代謝→注入とガード」の5フェーズで根本原因の順に潰す（フェーズ設計は design.md）。
「全消去して空から再出発する」案は採用しない。
棚卸しで高価値の教訓が現存することを確認済みであり、未参照の在庫はキュレーションで回収する。

### 実測ベースライン（改修効果の比較原点）

以下の数値は改修後に同一手順で再測定する（R-M2）。
測定手順はローカルデータ領域に数値とともに保存済みである。

- memory_search 11,876回中ゼロヒット56.6%（71日間、主ストア）
- 正解が実在する16クエリのベンチマークで、1位正解12.5%、5位以内50.0%、完全空振り50.0%。キーワード型クエリの的中率67%が自然文型40%を上回る
- memory_get_detail 到達率1.4%（索引→詳細のpull型2段設計が実働していない）
- 主ストア10,471件（生存9,706件、全件が同一project刻印）。ベクタ検索アクセス追跡10,133件中98.6%が一度も取得されていない
- 夜間統合は連日 clusters=3,123 / dup=0（圧縮ゼロのままLLMコストのみ発生）
- セッション注入は全文フォールバック時に直近30日のdont 209件で約7.5万字。健全時の実測は約8.2KB
- SessionStart注入はシンボリックリンク経由起動で出力ゼロバイト、exit 0（沈黙死）
- 統合キャッシュ汚染時は原則259個とガード正規表現64個が全ツール入力をブロック（2026-07-03に実発生、応急処置済み）
- アーカイブMarkdown 4,567件（約3.2MB、4ストア）はDBに存在せず、検索経路から構造的に到達不能
- 論理削除765件中751件のベクトルが残存し、backfillが再生成する
- 埋め込みモデル87MBが7ストアに完全重複（522MB回収可能）。旧世代 vectors.json（3072次元、95MB）は現行384次元DBに対する遺物

なおゼロヒット率56.6%は、その全体が故障ではない。
揮発状態の照会や存在しないプロジェクトへの絞り込みのように、0件が正しい応答であるクラス（**正しくゼロ件**）が混在している。
この区別は R-B6 と R-M2 で要件化する。

## Alignment with Product Vision

product.md の核心理念は「ユーザーは何もしなくていい」である。
この理念は、自動保存と自動注入と検索がすべて正しく機能して初めて成立するが、現状は注入が沈黙死し、検索が空振りし、統合が空転している。

本改修は新機能の追加ではなく、既存の設計思想（索引、統合、pull型、昇格、忘却）の結線を直す工事である。
product.md が掲げる解決課題のうち「毎回同じミスをする」「決定事項を忘れる」「コンテキスト膨張」「コンテキスト注入の無駄」に直接対応する。

### 事故経緯の設計制約への引き写し

過去事故の経緯を各1行で記録し、対応する設計制約を固定する。
記録がないと将来同じ仕組みが再発明される。

- **64正規表現事故**（2026-07-03）：統合キャッシュ汚染で自動生成されたガード正規表現64個が、一般的なコード片にまで誤マッチし全ツール入力をブロックした。制約：データからポリシーを自動生成する経路は自己DoSベクトルであり、ガードは承認制のみとする（R-C4）。
- **7.5万字注入事故**：サマリ欠落時の全文フォールバックが、可視の故障（注入されない）を不可視の肥大（7.5万字注入）に変換した。制約：欠損はfail-loud、全文フォールバックは持たない（R-C1）。
- **フリップフロップ事故**：v1系とv2系が同じ統合キャッシュを取り合い、注入原則とガードが日次で1個と259個の間を往復した。制約：統合キャッシュの書き込み主体は一系統のみ（R-A3）。
- **沈黙死事故**：CLIエントリ判定がシンボリックリンク経由の実行で不成立になり、出力ゼロバイト、exit 0 で終わり続けた。制約：判定不能の無言正常終了を禁止する（R-C2、禁止フォールバック#6）。
- **蘇生事故**：統合が削除したベクトルを、backfillが状態フィルタなしで毎セッション再生成した。制約：生死の判定は状態機械の一箇所に集約する（R-A2）。

## Requirements

要件は3系統（A：正本ストアと生死管理、B：派生インデックスと検索、C：注入とガード）と、共有の計測系統Mに分ける。
フェーズへの割り付けと実装設計は design.md、実施順序は tasks.md が持つ。

### 系統A：正本ストアと生死管理

#### R-A1 全量バックアップと再構築可能性

**User Story:** 運用者として、改修のどの段階からでも改修前の状態へ戻せるようにしたい。これはデータ移行プロジェクトであり、唯一のコピーを守れば以降の全手順が可逆になるため。

##### Acceptance Criteria

1. WHEN 改修の任意フェーズで問題が起きた THEN システムは Phase 0 で取得した全ストアの全量バックアップから、件数とチェックサムが一致する状態へ復元できること
2. WHEN スキーマ移行が実行される THEN 移行処理は開始前に自動バックアップを取得すること
3. IF バックアップの取得または復元リハーサルが失敗した THEN 移行処理は開始せずエラーで停止すること

#### R-A2 記憶の状態機械と削除済みの不可視性

**User Story:** メインエージェントとして、削除した記憶が検索にも注入にも二度と混ざらないでほしい。死んだIDが検索枠を占有し、削除の意図が裏で無効化されているため。

##### Acceptance Criteria

1. 全エントリは active / archived / deleted の3状態のいずれかを常に持ち、状態と各読み経路の可視性は design.md の不変条件として定義されること
2. WHEN いかなる読み経路（検索、注入、backfill、統合）が実行される場合も THEN deleted のエントリは返らないこと（PT-01）
3. WHEN エントリが deleted へ遷移する THEN 対応するベクトル行とFTS行は同一トランザクションで除去されること
4. deleted から active への遷移（蘇生）は存在しないこと。復元は archived からのみ許すこと
5. 既存の論理削除765件のうちベクトルが残存する751件は一括掃除されること

#### R-A3 新旧二重系統の清算

**User Story:** 運用者として、v1系とv2系が同じキャッシュを取り合う双頭構成をやめてほしい。毎セッション凍結済みデータをLLMで統合し直す沈黙コストと、日次のフリップフロップが続いているため。

##### Acceptance Criteria

1. WHEN セッションが開始される THEN v1 Markdown統合系（consolidate-worker のMarkdown読み書き、retag-worker）は起動しないこと。遮断は運用上の約束ではなくコード上の遮断であること
2. 統合キャッシュ（consolidated-dont / consolidated-config）への書き込み主体は夜間統合の一系統のみであること
3. アーカイブファイル自体（Markdown、vectors.json）は削除せず保持すること（Git差分レビューと人間監査性の要件）
4. WHEN Phase 4 が完了する THEN 死機能（UserPromptSubmit空回り配線、遮断済みv1経路、replaceIdデッドコード）は依存監査を経て物理削除され、機能ごとに死因が1行記録されていること。未コミットWIPの予測誤差ループは Phase 0 の作業ツリー清算（タスク0.0、退避のうえ除去）で処理する

#### R-A4 project帰属の信頼度付き修正

**User Story:** メインエージェントとして、projectフィルタ検索が構造的に0件になる状態を直してほしい。保存時の刻印がサーバ起動cwdで固定され、生存9,706件全件が同一project値になっているため。

##### Acceptance Criteria

1. WHEN 記憶が保存される THEN project はサーバ起動時cwdの固定値ではなく、呼び出し文脈由来の値で刻印されること
2. 各エントリは帰属信頼度（confirmed / inferred / unknown）を持つこと
3. WHEN projectフィルタ付き検索が実行される THEN unknown のエントリは既定で検索対象に含まれること（不明バケツをフィルタの裏に消さない）
4. 過去分のバックフィルは決定論的手掛かりのみで行い、LLMによる一括再分類は行わないこと（誤帰属はフィルタの裏に消える沈黙欠損になるため）
5. WHILE バックフィルが完了していない間 THEN projectフィルタは無効化されていること

#### R-A5 多並列アクセス耐性

**User Story:** 運用者として、複数エージェントの同時アクセスで書き込みが黙って失われない状態にしたい。

##### Acceptance Criteria

1. DBはWALモードで動作すること
2. busyタイムアウトが設定されること
3. WHEN 書き込みが失敗した THEN 失敗は計数と警報の対象になり、握りつぶされないこと

#### R-A6 追記型統合と系譜

**User Story:** オーナーとして、統合で記憶が壊れても原本へ遡って戻せるようにしたい。原本破壊のマージは不可逆なため。

##### Acceptance Criteria

1. WHEN 統合（マージ）が実行される THEN マージ結果は新レコードとして追加され、原本レコードの本文は変更も物理削除もされないこと
2. マージ結果は系譜（merged_from）を持ち、原本へ遡れること
3. WHEN 新しい決定が古い決定を陳腐化させる THEN supersedes 関係が記録され、参照時に新旧が判別できること。矛盾解決は統合の一級要件であること
4. 夜間統合は1晩あたりの上限件数を持ち、dry-runレポートを経由して再開できること
5. 初回の一括統合は最大の事故日と認識し、少量バッチと人間サンプル確認から始めること
6. ラベル付きペアでの誤統合率が確定閾値以下であること（MG-01。仮基準5%以下、確定値はゲートG3で記録）

#### R-A7 確定原則への昇格の人間ゲート

**User Story:** オーナーとして、常時注入される確定原則の昇格を自分の承認制にしたい。誤記憶1件が自動昇格から常時注入に至ると全案件を汚染する自己増殖ループになり、記憶ストアは認証なしの書き込み口としてプロンプトインジェクションの永続化ベクトルにもなり得るため。

##### Acceptance Criteria

1. 確定原則は出所ティア（owner_confirmed / agent_observed）を持つこと
2. WHEN 常時注入層への昇格が行われる THEN オーナーの明示承認を経ていること。未承認の原則は注入されないこと
3. 確定原則は出所、証拠リンク（元記憶ID群）、有効期限（TTLまたは再検証日）を必須で持つこと（事実は腐る）
4. 自動昇格の経路はコード上存在しないこと

### 系統B：派生インデックスと検索

#### R-B1 段階フォールバック検索と候補プール

**User Story:** メインエージェントとして、自然文でもキーワードでも記憶が引けるようにしたい。現状はクエリ全体のフレーズ一致しか効かず、平均38字の自然文クエリが構造的に空振りするため。

##### Acceptance Criteria

1. WHEN 検索が実行される THEN フレーズ→AND→OR→ベクトル→新着 の順で段階フォールバックし、各段の発火が計数されること
2. FTS側とベクトル側の候補プールはそれぞれ20件目安へ拡大され、最終値は実測で確定されること
3. 複数経路の結果はRRFで統合順位化されること
4. 新着フォールバックの発火は応答に明示されること（設計されたフォールバックの3条件は design.md）

#### R-B2 順位の再設計と読み経路の無副作用

**User Story:** メインエージェントとして、関連する記憶が上位に来てほしい。現状の最終順位は関連度でなく時系列で、FTSランクもベクトル距離も捨てられているため。

##### Acceptance Criteria

1. 最終順位は 関連度 × 時間減衰 で決まること。時系列単独の並びは廃止すること
2. recency はランキング素性として残すこと。コーディング記憶は新しい決定が古い決定を上書きするドメインであり、純関連度は廃止済み決定を上位に出すため
3. WHEN 検索が実行される THEN 読み経路はいかなるエントリの intensity も timestamp も変更しないこと。読み取りによる書き換えは時間減衰順位を汚染するため（監査D13の破壊的自動昇格は廃止し、利用実績の反映は既存の検索スコア加点に一本化する）

#### R-B3 自己検索性

**User Story:** メインエージェントとして、保存した記憶がその内容自身で必ず見つかることを保証してほしい。

##### Acceptance Criteria

1. WHEN 生存する任意のエントリの本文をクエリとして検索する THEN 当該エントリ自身が上位10件に入ること。全件を対象にプロパティテスト化すること（PT-04）
2. 本文がFTSトークナイザの最短長（trigram=3文字）未満のエントリは達成不能があり得るため対象外とし、除外件数を出力すること（除外閾値の根拠はスパイク0.2の実測記録）

#### R-B4 距離尺度の型封じ

**User Story:** 実装者として、L2距離とコサイン類似度の取り違えを型エラーで検出したい。閾値0.6の尺度取り違えが統合機能を1年分空転させたのは規約では防げなかったため。

##### Acceptance Criteria

1. L2距離とコサイン類似度は別の型として表現され、混同はコンパイルエラーになること
2. 閾値は尺度種別と同一構造体で保持されること
3. WHEN 距離と閾値が比較される THEN 同一尺度同士であることが型で保証されていること

#### R-B5 埋め込みモデルの版数管理と混在禁止

**User Story:** 運用者として、埋め込みモデル差替えの過渡期に新旧ベクトルが黙って混在しない状態にしたい。混在比較は沈黙破損であるため。

##### Acceptance Criteria

1. 各ベクトルは生成モデルの識別子を持つこと
2. WHILE 全件再埋め込みが完了していない間 THEN 新モデルによる検索は起動時アサートで拒否されること
3. モデル差替えの判断は日本語実測評価の結果に基づくこと

#### R-B6 ゴールデンセット評価と「正しくゼロ件」

**User Story:** オーナーとして、検索改修の効果を実クエリで測りたい。fixture合格だけで切り替えて実運用で悪化する事故を防ぐため。

##### Acceptance Criteria

1. 評価は実ログ由来のゴールデンクエリ集合（形式は design.md、実体はローカルデータ領域）で行うこと
2. ゴールデンセットは「正しくゼロ件」クラスを含めてラベル付けすること。ゼロヒットを一律に悪と定義すると、ノイズを当てる方向へ最適化されるため
3. WHEN ゲートG2が実行される THEN 正解実在クラスの recall@5 が、同一ゴールデンセットを旧検索で実行して再測定した基準値（タスク2.3で記録）を上回ること。母集団の異なる過去計測値（16問ベンチマークの0.500）を合格基準に流用しない
4. WHEN ゲートG2が実行される THEN 「正しくゼロ件」クラスの全問で0件が返ること
5. カットオーバーは新旧シャドー並走の実測比較後に行うこと

#### R-B7 アーカイブのサルベージ

**User Story:** オーナーとして、検索経路から到達不能になっているアーカイブ4,567件を放置せず、回収するか去就を確定させたい。

##### Acceptance Criteria

1. アーカイブMarkdownの4,567件は、キュレーション（LLM判定と人間サンプル確認）を経てDBへ取り込むか、コールド保管のまま索引だけ張るかが確定され、実行されること
2. WHILE 検索評価が進行中の間 THEN 評価コーパスは凍結され、サルベージ流入と分離されていること

#### R-B8 埋め込みモデルの共有キャッシュと遺物の廃棄

**User Story:** 運用者として、同一モデル87MBの7重複と旧世代の埋め込みキャッシュを整理したい。

##### Acceptance Criteria

1. 埋め込みモデル実体は共有キャッシュ1箇所に集約され、ストア毎の重複522MBが解消されること
2. 旧世代 vectors.json（3072次元）はバックアップ取得後に廃棄されること

### 系統C：注入とガード

#### R-C1 注入バジェット（消費側トークン管理）

**User Story:** メインエージェントとして、セッション冒頭の注入が確定した最小限の情報だけになってほしい。7.5万字の全文注入は大事な1行を埋没させ、遵守率を自ら下げるため。

##### Acceptance Criteria

1. 常時注入は最小索引と承認済み確定原則のみで構成されること
2. 注入バジェットは消費側モデルのトークン数で管理されること。文字数管理は日本語で大きく乖離するため
3. WHEN 注入素材（サマリ等）が欠損している THEN 全文へフォールバックせず、当該部分をスキップして計数し警報すること（fail-loud）
4. 任意のDB状態において注入がバジェット以下であること（PT-02）

#### R-C2 SessionStart注入の修復とバジェットの同時着地

**User Story:** オーナーとして、動いていない自動注入を直したい。ただし直した瞬間に7.5万字注入が復活しない形で。

##### Acceptance Criteria

1. WHEN CLIがシンボリックリンク経由で実行される THEN エントリ判定は実体パスの解決によって成立し、注入本文が出力されること
2. 注入修復とバジェット強制は同一タスクの同一コミットで着地すること。修復を先行単独で入れると全文注入が全セッションで復活するという順序制約があるため
3. WHEN エントリ判定が成立しない THEN 無言の exit 0 ではなくエラーが出力されること

#### R-C3 固定付帯ブロックのpull化と全文ダンプの上限

**User Story:** メインエージェントとして、検索のたびに同じ固定5件が無条件で付いてくるpush型配布をやめてほしい。

##### Acceptance Criteria

1. WHEN 検索が実行される THEN angerHistory等の固定付帯ブロックは無条件では付帯しないこと（pull型へ移行）
2. memory_get_context は件数と分量の上限を持ち、全件全文ダンプ（実測で約69万字）を返さないこと

#### R-C4 ガードの承認制（自動生成全廃）

**User Story:** オーナーとして、ガードが自分の作業を止める事態を自分で止められるようにしたい。ガードを直すツールまでブロックするロックアウトが最悪形であるため。

##### Acceptance Criteria

1. ガードパターンの自動生成経路はコード上存在しないこと（全廃）。データからポリシーを自動生成する経路は自己DoSベクトルであるため
2. 各ガード規則は出所（事故ID）とTTL（失効日時）を必須で持ち、再確認がなければ失効すること
3. アクティブなガード規則数は設定上限以下であること（PT-03）
4. WHEN 直近のブロック率が閾値を超える THEN サーキットブレーカが全ガードを自動停止し警報すること
5. MCPプロセスの外部から効くキルスイッチ（ファイル存在による即時全停止）が存在すること
6. 既存の64パターンは出所を採掘し、実事故由来と確認できたもののみ承認制で残すこと。残数は数本を想定

### 系統M：計測と検証基盤

#### R-M1 可観測性カウンタと警報

**User Story:** 運用者として、故障が沈黙せず数値で見える状態を、他のどの改修よりも先に手に入れたい。計測は最初の出荷物である。

##### Acceptance Criteria

1. ゼロヒット率、注入トークン数、統合件数、ガードブロック件数、蘇生件数の5指標が継続計測されること
2. 各指標は閾値警報を持つこと
3. 5指標の計測は Phase 0 で出荷されること（以降の全改修の効果測定の前提）

#### R-M2 KPIとベースライン再測定

**User Story:** オーナーとして、改修の成否を「ゼロヒット率が下がったか」ではなく「必要な時に見つかり、役に立ったか」で判定したい。

##### Acceptance Criteria

1. 主KPI候補は「必要になった時に見つかった率」とし、ゼロヒット率単独をKPIにしないこと
2. 「当たった記憶は正しく役に立ったか」の精度指標を併設すること。ヒット率が高くても当たるのが廃止済み決定なら、ゼロヒットより有害であるため
3. 改修後の測定は、ベースライン（本書冒頭）と同一手順で行うこと

#### R-M3 検証資産の分離

**User Story:** PdMとして、検証の仕組みが実装の写経にならないよう、作る人を分けたい。

##### Acceptance Criteria

1. ゴールデンセット、ラベル付きペア、ゲートスクリプトは実装者以外（検証役）が作成すること
2. ゴールデンセットと実データスナップショットの実体は公開リポジトリに置かず、ローカルデータ領域にGit外で保持すること。本Specは形式とポインタのみを定義する
3. ゲートは秘密値をマスクした実データスナップショットで走らせ、合成英語データで代替しないこと。合成英語データでは日本語トークナイザの欠陥がすり抜けるため
4. 全ゲートは空DBでの空振り合格を防ぐ最小件数アサートを前提に持つこと

## Non-Functional Requirements

### Code Architecture and Modularity

- **Single Responsibility Principle**: 各ファイルは単一の明確な責務を持つ
- **Modular Design**: 検索パイプライン、注入ビルダ、ガードレジストリ、カウンタは独立モジュールに分離する
- **Dependency Management**: CLIとMCPツールの双方が同一の実装モジュールを呼ぶ構造にする。読み経路ごとの実装差分が今回の事故群（可視性の不整合、二重系統）の温床であったため
- **Clear Interfaces**: 状態機械と距離尺度は型でインターフェースを固定する

### Performance

- 検索応答は現行水準（中央値420ms）から劣化させない
- SessionStartフックのタイムアウト（5秒）以内に注入本文を返す。埋め込みモデルの初回ロードに起因する3秒超の遅延（実測最大43.6秒）はフック経路で発生させない

### Security

- 本リポジトリは公開である。Spec、findings、ゲート出力には、個人ホームの絶対パス、実在の組織名と個人名、経営数値、記憶エントリの生本文、実クエリ本文を含めない
- ゲートとテストの出力は件数、率、ID、ハッシュのみで構成し、記憶本文を転記しない
- 外部LLMへ記憶本文を投入する既存経路のredact水準を、本改修で現状から縮小しない

### Reliability

- 全フェーズにロールバック手順が事前定義されていること（design.md の各フェーズ④）
- 欠損はfail-loud（スキップと計数と警報）で扱う。design.md の禁止フォールバック一覧に該当する実装はレビューで差し戻す
- LLM出力の業務整合性検査はwarning設計とし、throwにしない（詳細は design.md のLLM呼び出し設計）

### Usability

- 検索応答のhintは、発火したフォールバック段とヒット状況を利用者（エージェント）に伝える
- ガードのブロック表示には出所（事故ID）を含め、利用者が異議の宛先を特定できるようにする
