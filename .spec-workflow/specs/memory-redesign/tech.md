# Technology Stack

> 本書は記憶の代謝再建フィーチャー（memory-redesign）のSteering文書である。
> 「Technical Decisions & Rationale」の各判断は2026-07-03のPdM統合設計判断メモ（ローカル保管）で確定済みであり、実装者は変更しない。疑義があれば実装前に異見として返す。

## Project Type

STDIOベースのMCPサーバーに、Hooks連携のCLI群と夜間バッチ（launchd）を束ねたローカル実行ツール。
npmパッケージとして配布され、利用者の各リポジトリにデータ領域（`.wasurenagusa/`）を持つ。

## Core Technologies

### Primary Language(s)

- **Language**: TypeScript 5系
- **Runtime**: Node.js 18以上（ES2022ターゲット）
- **Module System**: ESM（NodeNext。相対importは `.js` 拡張子付き）

### Key Dependencies/Libraries

| @modelcontextprotocol/sdk | MCPサーバー実装の基盤 |
| better-sqlite3 | SQLiteアクセス（同期API） |

### ライブラリのピン留めと実在確認スパイク

- 改修が触る領域（sqlite-vec、FTS5トークナイザ、埋め込みモデルまわり）は、バージョンをロックファイルで固定し、Spec本文にも使用バージョンを明記する
- これらの領域はLLM実装者がAPIを幻覚しやすい。仮想テーブルの構文、トークナイザの指定方法、距離メトリクスの既定値は、ドキュメントの記憶ではなく**実在確認スパイク**（最小コードでの実行確認）で確かめてから本実装に入る。スパイクはPhase 0系タスクとして先頭に置く

### Application Architecture

MCPツール層（`src/tools/`）とHooks CLI層（`src/cli/`）が、ストレージ層（`src/storage/`）とベクトル層（`src/vector/`）を共有する構成である。
責務の地図は structure.md を正本とする。

現状はストレージがv1（Markdown）とv2（SQLite）の二重系統になっており、統合キャッシュを両系統が上書きし合っている。
清算方針は次のとおり。

- 書き込みの正本はSQLite（v2）である
- v1系統の書き込み経路はPhase 0でコード上物理遮断する（凍結の約束ではなく、書けない状態にする）
- v1のアーカイブファイル自体は保持する（削除しない。理由はstructure.mdの「触ってはいけない領域」）

### Data Storage

- **正本**：プロジェクト毎の `.wasurenagusa/memory.db`（エントリ本文、FTS5索引、vec0埋め込み 384次元、統合キャッシュ、stash、テーマ）
- **スキーマ版数**：`schema_version` テーブルの `MAX(version)` で管理する（SQLiteの `user_version` プラグマではない）。コミット済みHEADのベースラインはv5である（2026-07-03の予測誤差ループ保全コミット8b915a5がv5を占有したため、本Spec起草時点の想定であったv4から1段繰り上がっている）。本改修の移行連鎖は5→6→7→8とする
- **遺物**：v1のMarkdownファイル群と旧世代 `vectors.json`（実測3072次元、95MB。バックアップ後に廃棄する）
- **状態機械**：記憶は active／archived／deleted の3状態を持ち、各読み経路での可視性を不変条件として定義する。「削除済みは、いかなる読み経路（検索、注入、埋め込み補完、統合）からも返らない」をプロパティテスト化する
- **並列書き込み**：複数セッションとワーカーが同時に書く実態に合わせ、WAL、busyタイムアウト、書き込み失敗の計数を入れる。失敗の握りつぶしは禁止

### External Integrations

- **LLM**：genkit抽象経由のマルチプロバイダ。既定は軽量フラッシュ系モデル。特定ベンダSDKの直書きは是正対象（プロバイダ設定が効かなくなるため）
- **APIキー**：環境変数で解決する（プロジェクトの `.env`、なければホーム側のグローバル設定）。実値をコードやドキュメントに書かない
- **外部送出前のredact**：記憶本文や会話ログを外部LLMへ送る全経路（統合、重複判定、分析）に、機密マスク処理を共通適用する

## Development Environment

### Build & Development Tools

- **Build**: tsc（`npm run build`。CLIエントリに実行権限を付与）
- **Test**: vitest（`npm test`）。テストは実装と同ディレクトリの `*.test.ts`
- **発効制約**：TypeScriptのソース修正だけでは実行系に反映されない。`npm run build` で `dist/` を再生成し、稼働中のMCPサーバー・フックCLIプロセスを再起動して初めて全起動経路に発効する。commitやpushの完了は発効を意味しない。2026-07-05、検索ヒントとproject帰属の修正がコミット済みであるにもかかわらず、稼働中プロセスが起動時に読み込んだ旧コードのまま動き続け「push済みなのに未発効」という事象が実際に発生した。検証は必ず新規に起動したプロセスで行う（`scripts/verify/production-path-smoke.mjs` が dist/index.js を新規起動して検証するのはこの制約に対応するため）

### Code Quality Tools

検証まわりは、この改修で特に次の規律を守る。

- **ゲートは実行可能スクリプト**：フェーズ完了の検証ゲートは散文ではなくスクリプトにする。完了定義に「ゲートスクリプトの実行出力貼付」を含め、exit codeではなく結果本文を読む
- **ゲートは実データ相当で走らせる**：匿名化した実データスナップショットを使う。合成英語データでは日本語トークナイザの欠陥がすり抜ける。空DBでの空振り合格を防ぐ最小件数アサートをゲートの前提に置く
- **検証データは二層に分ける**：リポジトリ内に置くのは機密ゼロの合成日本語ミニfixtureのみとし、機構検証（配線、移行、不変条件）専用に使う。recallやトークナイザ実効といった品質の測定は、git外のローカル実データ層（匿名化スナップショットとゴールデンセット）でのみ行う。合成fixtureの合格を品質の根拠にしない
- **ゴールデンセットは実装者が書かない**：実装の写経になるため、Spec側で先に凍結し、検証役を分離する。実クエリ由来のため実体は公開リポジトリに置かず、ローカルデータ領域にgit外で保持する。Specには形式とポインタのみ定義する
- **症状とテストの対応表**：8症状→禁止要件→テストIDの対応表をSpecに置き、各事故の経緯を1行ずつ引き写す
- **受け入れ基準は挙動で書く**：ゴールデンセットでのrecall@k、消費側トークンで測った注入上限、ラベル付きペアでの誤統合率、不変条件のプロパティテスト（削除済みは返らない、任意DB状態で注入バジェット以下、ガード規則数上限）
- **既存の評価・検証スクリプトの現況**：`scripts/eval/self-retrieval.mjs` は自己検索率の回帰計測ハーネスであり、現行のローカル埋め込みAPI（`embed(text, usage)` の用途引数必須化）に追従済みである。`scripts/verify/production-path-smoke.mjs` は本番起動経路（dist/index.js＋stdio JSON-RPC）でのスモークテストの正本であり、design.md Testing Strategy が定める本番経路検証の実行主体はこのスクリプトである

## Technical Requirements & Constraints

### Performance Requirements

- SessionStart hookのタイムアウト（5秒）内に注入本文を生成し終える
- 常時注入は消費側モデルのトークン数で上限管理する。健全時の注入実測は約8.2KB（2026-07-03監査）で、これを桁で超えない
- 主ストア実測の1万件規模（生存9,706件、DB 47MB。2026-07-03監査）で検索と夜間統合が成立する

### Compatibility Requirements

- **Platform Support**: Node.js 18以上。動作実績はmacOS中心で、非macOSは未検証（2026-07-03監査）
- **MCP Client**: 動作実績はClaude Code。他クライアントは未検証

### Security & Compliance

- **公開リポジトリ制約**：機密（個人パス、実在社名、個人名、経営実数、記憶エントリの生本文、実クエリ本文）をコード、Spec、テストfixtureに書かない。fixtureは合成値を使う
- **脅威モデル**：記憶ストアは認証なしの書き込み口であり、プロンプトインジェクションの永続化ベクトルになり得る。だから確定原則への昇格に人間ゲートを置く（Decision Log 12）
- **ガードの自己DoS対策**：ガードがガードを直すツールまでブロックするロックアウトが最悪形である。ブロック率のサーキットブレーカと、MCP外部から効くキルスイッチを初期仕様に含める

### Scalability & Reliability

- 全ストアの全量バックアップと再構築可能化を最初に行う。これはデータ移行プロジェクトであり、唯一のコピーを守れば以降の全手順が可逆になる
- 各フェーズに、スキーマ移行手順、non-goals、実行可能な検証ゲート、事前定義のロールバック手順の4点を必ず持たせる

## Technical Decisions & Rationale

### Decision Log

以下は確定済みの判断である（2026-07-03のPdM統合設計判断）。

1. **フェーズ順序は「止血→土台→検索→代謝→注入・ガード」**：一番目立つ検索から着手する案は不採用。汚染進行中のデータ上に検索を作ると、後の再埋め込みと帰属修正で評価が全部無効になる
2. **距離尺度の型封じ**：L2距離とコサイン類似度を別型にし、閾値を尺度と同一構造体で保持する。規約ではなく型エラーで再発を防ぐ。背景に、L2距離へコサイン類似度用の閾値を適用したことによる統合不発（連日dup=0）がある
3. **追記型統合**：マージ結果は新レコードとして書き、原本は系譜ポインタ付きで保持する。原本破壊のマージは不可逆なので禁止。夜間統合には1晩あたりの上限件数と、dry-runレポートを経由した再開手順を持たせる。初回一括統合は最大の事故日と認識し、少量バッチと人間サンプル確認から始める
4. **記憶の状態機械**：active／archived／deleted の3状態と読み経路ごとの可視性を不変条件として明文化し、プロパティテストで固定する
5. **注入はトークン単位バジェット**：常時注入は最小索引と承認済み確定原則のみ。バジェットは消費側モデルのトークン数で管理する（文字数管理は日本語で大きく乖離する）。全文フォールバックは廃止し、固定付帯ブロックはpull型へ移行する
6. **fail-loud原則**：欠損はスキップして計数する。禁止フォールバックはSpecに列挙で明記する。この系の事故は全部「善意のgraceful fallback」が可視故障を不可視肥大に変換して起きた。安全側のつもりでフォールバックを再導入しない
7. **recencyはランキング素性として残す**：順位は関連度と時間減衰の積。コーディング記憶は新しい決定が古い決定を上書きするドメインであり、純関連度は廃止済み決定を上位に出す
8. **段階フォールバック検索とRRF統合**：フレーズ→AND→OR→ベクトル→新着の順に落とし、候補プールを拡大（5+5から20+20目安。最終値は実測で確定）してRRFで統合する
9. **日本語トークナイザの先行スパイク**：FTS5のトークナイザ変更のみで再計測し、ゼロヒットへの主因寄与を確定してから検索再設計の要否と規模を判断する。安価で情報量の多い実験を再設計の前に置く
10. **埋め込みモデル差替えは版数管理つき**：日本語実測評価を経て多言語対応モデルへの差替えを判断する。モデル版数列を追加し、全件再埋め込みの完了ゲートを通過するまで新旧ベクトルの混在比較を禁止する（混在は沈黙破損）。モデルはホーム側の共有キャッシュに一本化する（7プロジェクト重複522MBの回収）
11. **プロジェクト帰属は信頼度列つきで修正**：帰属信頼度列を追加し、不明バケツは既定で検索対象にする。LLMによる一括再分類は不採用（誤帰属はフィルタの裏に消える沈黙欠損になる）。バックフィル完了までprojectフィルタは無効化する
12. **確定原則への昇格は人間ゲート**：記憶に出所ティア（オーナー確認済み／エージェント観測のみ）を持たせ、常時注入層への昇格はオーナー承認制にする。誤記憶1件が自動昇格から常時注入に乗ると全案件を汚染する自己増殖ループになるため、構造的に遮断する
13. **確定原則は出所、証拠リンク、有効期限を必須化**：元記憶へのリンクとTTL（または再検証日）を持たせる。事実は腐る。新決定が旧決定を陳腐化させる関係の明示（矛盾解決）を統合の一級要件にする
14. **ガードは自動生成全廃、承認制のみ**：出所（事故ID）必須、TTL付き（再確認なければ失効）。既存64パターンには実事故由来の本物が混在するため、全廃前に出所を採掘し、確認済みの数本だけ承認制で残す。設計制約として明文化する：データからポリシーを自動生成する経路は自己DoSベクトルである
15. **死機能は依存監査つきで物理削除し、死因を1行記録する**：記録がないと将来再発明される。予測誤差ループ（実データ0件）は本判断メモの後、コミット8b915a5（オーナー裁定2026-07-03）でHEADへ保全済みとなった。当初方針（未コミットWIPとして退避パッチ化のうえ破棄）は前提を失っており、存置か除去かの扱いはタスク0.0で判断する
16. **カットオーバーは新旧シャドー並走の実測比較後**：fixture合格だけで切り替えない
17. **注入修復とバジェット強制は同一タスクで同時着地**：SessionStart注入の沈黙死（シンボリックリンク実パス未解決）の修復を先行単独で入れると、7.5万字注入が全セッションで復活する。順序制約として固定する

### 不採用とした代替案

- 全消去して空から再出発：不採用。高価値教訓の現存を棚卸しで確認済みであり、キュレーションで回収する
- 検索エンジン全廃とagentic grep専任：不採用。ただし段階フォールバックとエージェント側の再クエリ習慣は取り込む
- 旧Markdown系統の物理削除：不採用。git差分レビューと人間監査性は要件であり、コールド保管と系譜保持に変更
- Markdownを唯一の正本にしSQLiteを使い捨て派生物化：今回は不採用（変更半径が大きすぎる）。ただし「派生物は全再構築可能」という性質は状態機械とバックアップ要件として取り込む
- 注入ゼロ実験：部分採用。注入前後の挙動比較を固定タスクスイートで実測してから削り幅を決める

## Known Limitations

- 現行実装の欠陥は2026-07-03監査で14系統に整理済み（監査レポートは `docs/findings/` 配下のローカル文書。同ディレクトリはgit追跡外）。根本原因は上記3本に帰着する
- LLMプロンプトのうち会話分析用の1本が288行（コミット済みHEADで確認）あり、決定論的な計算（閾値判定、加点、カテゴリ検証）が混入している。コード側への移譲が改修対象
- 未検証範囲：非macOS環境、Claude Code以外のMCPクライアント、vec0の距離分布の実測サンプリング
