## Product Purpose

**最高のバイブコーディング体験を提供する**自律動作型MCPサーバー。

**核心理念: ユーザーは何もしなくていい**

会話中の重要情報をHooks連携で**自動保存**し、セッション開始時に**自動注入**することで、AIアシスタントが「学習する」体験を提供する。さらに、開発者が寝ている間にプロジェクトドキュメントを自動更新し、5時間レート制限ウィンドウを最適活用する。手動操作は完全にオプション。

### 解決する課題
1. **毎回同じミスをする** - API URL間違い、ポート間違い、ログを読まない等
2. **決定事項を忘れる** - 技術選定、アーキテクチャ決定が消える
3. **やったことを覚えていない** - 実装済み機能を再実装しようとする
4. **ユーザーの怒りを理解しない** - 同じ指摘を何度もさせる
5. **コンテキスト膨張** - セッションが長くなるとパフォーマンス劣化
6. **よく使うコマンド・クエリを毎回探す** - テストAPI、DBクエリ等を覚えていない
7. **Specドキュメントが陳腐化する** - 日々の改修でコードとドキュメントが乖離していく
8. **5時間レート制限が無駄になる** - 寝ている間のトークン枠が使われない

## Target Users

### Primary User
- **Claude Code利用者**（開発者）
- 日常的にClaude Codeでプログラミングを行う
- プロジェクトごとに異なる設定・規約がある
- 同じミスの繰り返しにフラストレーションを感じている

### Pain Points
- 「何度言えば分かるの？」という体験
- 毎セッション、同じ説明を繰り返す手間
- 長いセッションでのレスポンス低下
- プロジェクト固有のルールが守られない
- よく使うテストコマンドを毎回教え直す手間

## Key Features

### 自動実行（Hooks連携・CLIスクリプト）
1. **wasurenagusa-context** - 【SessionStart Hook】config+dontを標準出力→コンテキスト注入
2. **wasurenagusa-analyze** - 【Stop Hook】会話を分析し、重要情報を自動保存

### MCPツール（AIが呼び出し）
3. **memory_get_context** - config+dont取得（Hooksでも自動実行）
4. **memory_search** - 軽量インデックス検索（タイトル+タグのみ返却でトークン節約）
5. **memory_get_detail** - 必要なエントリのフル詳細を取得

### 手動ツール（オプション）
6. **memory_save** - 明示的に保存したい時だけ使用
7. **memory_delete** - 不要エントリの削除（ID指定、複数一括削除対応）

### Spec自動更新（Scheduler連携）
8. **wasurenagusa-spec-update** - 【cron/systemd timer】5時間5分サイクルでClaude Code CLIを起動し、Specドキュメントを自動更新
9. **変更ログ記録** - Stop Hook（wasurenagusa-analyze）実行時に、セッション中に変更されたファイル一覧を変更ログに記録
10. **タスクキュー** - 変更ベース更新・ローテーション更新を優先度付きキューで管理。1サイクル1タスク実行
11. **Keep-Alive** - タスクがない場合でもpingを送信し、5時間ウィンドウを回転させる

### コア機能
12. **Gemini自動判定** - Gemini 3 Flash（gemini-3-flash-preview）で会話を自動分類・保存
13. **プロジェクト横断記憶** - シンボリックリンクで`.wasurenagusa/`を集約。各エントリにproject/scopeフィールドを持ち、フィルタリング可能
14. **AIリトライ検出** - AI自身の失敗パターンを自動検出・記録
15. **動的記憶取得** - セッション開始時は最小限の注入（dont全件+configタイトル一覧）。それ以外はAIが必要な時にmemory_search/memory_get_detailで動的に取得（「必要な時に思い出す」体験）
16. **重複検出・自動マージ** - Geminiベースのセマンティック重複検出。同じテーマのエントリは自動置換でコンテキスト汚染を防止
17. **メタ情報による諦め検知** - メッセージ長の急減少やポジティブ反応の不在を数値で検知し、テキストパターンだけでは拾えない「沈黙の諦め」を捕捉
18. **プロンプト外部化** - 分析プロンプトを`prompts/`ディレクトリにテキストファイルとして管理。デプロイなしでプロンプト改善可能
19. **dont統合（L3圧縮）** - SessionStart時にGeminiで多数のdontエントリ（例:49件）を5-6個の行動原則に統合。元エントリは保持したまま、コンテキスト注入量を36KB→3-4KBに大幅削減

## Memory Categories

| カテゴリ | 用途 | 例 |
|----------|------|-----|
| **config** | 設定情報 | API URL、ポート、認証情報、環境変数 |
| **dont** | やってはいけないこと | ユーザーが怒ったこと、過去のミス、禁止事項 |
| **decision** | 決定事項 | 技術選定、アーキテクチャ、命名規則 |
| **log** | 作業ログ | 実装した機能、解決したエラー |
| **snippet** | よく使うコマンド・クエリ | テストAPIコマンド、DBクエリ、便利スクリプト |

## Memory Metadata

各エントリには以下のメタデータが自動付与される：

| フィールド | 用途 | 取得方法 |
|-----------|------|---------|
| **project** | どのプロジェクトに紐づく知識か | cwdのディレクトリ名から自動取得 |
| **scope** | 知識の領域分類 | Gemini分析で自動判定 or 手動指定 |

### scope候補

| scope | 想定される知識 |
|-------|--------------|
| `frontend` | UI実装、状態管理、デザインパターン |
| `backend` | API設計、DB構造、サーバー処理 |
| `infra` | デプロイ、GCP設定、CI/CD、環境変数 |
| `design` | UI/UXの方針、デザインシステム |
| `spec` | 仕様決定、要件定義、ビジネスロジック |
| `ai` | LLM連携、プロンプト設計 |
| `general` | プロジェクト横断・分類不能（デフォルト） |

候補以外の自由入力も可。

## Use Cases

### UC1: ユーザーの怒りをトリガーとして記録
**シナリオ**: ユーザーが「なんでこんなこともわかんねーのよ」「さっき言ったでしょ」と怒る
**トリガー**: Geminiがユーザーの怒り・不満を検出
**アクション**: `dont`カテゴリに自動保存
**効果**: 次回以降、同じミスを事前に防止

### UC2: AI自身のリトライパターンを検出して記録
**シナリオ**: AIがAPIを何度も叩き直す、DBクエリを何回も発行する
**トリガー**:
- 同じAPIエンドポイントを短時間に3回以上実行
- 同じDBクエリを短時間に3回以上発行
- 同じエラーが繰り返し発生
**アクション**: `dont`カテゴリに「正しいやり方」を自動保存
**効果**: 次回は最初から正しい方法で実行

### UC3: よく使うテストAPIコマンドを保存
**シナリオ**: 「このAPIのテストはこのコマンドで」とユーザーが教える
**トリガー**: 手動保存 or Geminiが「これはよく使うコマンド」と判定
**アクション**: `snippet`カテゴリに保存
**効果**: memory_search "API テスト" で即座に取得可能

### UC4: プロジェクトの前提情報を保存
**シナリオ**: 「このプロジェクトはポート3000固定」「本番DBはFirestore」
**トリガー**: 手動保存 or Geminiが設定情報と判定
**アクション**: `config`カテゴリに保存
**効果**: memory_get_contextで毎セッション自動注入

### UC5: DBクエリのテンプレートを保存
**シナリオ**: 「ユーザー一覧取得はこのクエリ」とユーザーが教える
**トリガー**: 手動保存
**アクション**: `snippet`カテゴリに保存
**効果**: memory_search "ユーザー クエリ" で即座に取得可能

### UC6: Specドキュメントの自動更新（変更ベース）
**シナリオ**: 日中の作業で`src/api/handler.ts`と`src/models/user.ts`を改修した
**トリガー**: Stop Hook → wasurenagusa-analyzeが変更ファイルをログに記録 → 次のスケジューラサイクルで検出
**アクション**: Claude Code CLI（ヘッドレス）がプロジェクトのSpecドキュメントを変更内容に基づき更新
**効果**: 翌朝にはドキュメントが最新化されている

### UC7: Specドキュメントのローテーション更新
**シナリオ**: 変更ログはないが、プロジェクトAのSpecが30日前に最終更新
**トリガー**: スケジューラサイクルでタスクキューが空 → 最終更新日が古いプロジェクト順にローテーション
**アクション**: Claude Code CLIがコードベースとSpecの乖離を確認・更新
**効果**: 長期間触っていないプロジェクトのドキュメントも鮮度を保つ

### UC8: 5時間ウィンドウのKeep-Alive
**シナリオ**: 深夜帯で変更ログもローテーション対象もない
**トリガー**: 5時間5分サイクルのスケジューラ実行
**アクション**: `claude -p "ping"` で最小限のリクエストを送信
**効果**: 翌朝の作業開始時に5時間ウィンドウがリセット直後の状態になる

## Auto-Detection Triggers

### ユーザー起因トリガー
- **怒りの検出**: 「なんで」「何度言えば」「さっき言った」等のフレーズ
- **不満の検出**: 「違う」「そうじゃない」「だから」等のフレーズ
- **悲しみ・失望の検出**: 「期待してたのに」「残念」「がっかり」等のフレーズ
- **諦めの検出（最も深刻）**: 「もういいや」「自分でやる」+ メタ情報（メッセージ長の急激な減少、ポジティブ反応の長期不在）
- **明示的な指示**: 「覚えておいて」「これ忘れないで」「次からは〜」

### AI起因トリガー（リトライ検出）
- **API多重実行**: 同じエンドポイントを短時間に3回以上実行
- **DBクエリ多重発行**: 同じクエリを短時間に3回以上発行
- **エラー繰り返し**: 同じエラーが3回以上発生
- **ファイル多重編集**: 同じファイルを短時間に5回以上編集

## Product Principles

1. **自律自動が基本、手動はオプション**: ユーザーは何もしなくても記憶が蓄積・活用される
2. **Hooks連携で完全自動化**: SessionStart/Stopで自動実行、ユーザー介入不要
3. **コンテキストを圧迫しない軽量設計**: 検索時はインデックスのみ返却、必要なものだけフル取得
4. **必要な時に思い出す**: SessionStart時はdont全件+configタイトル一覧のみ注入。それ以外はAIが動的にmemory_search/memory_get_detailで取得
5. **ローカル完結・セットアップ簡単**: npm installだけで動作、外部サービス最小限
6. **プロジェクト横断 + スコープ分類**: シンボリックリンクで`.wasurenagusa/`を集約管理。project/scopeフィールドでフィルタリング
7. **トリガーワード不要**: LLM（Gemini）で自動判定、自然な会話のまま学習
8. **AI自身の失敗も学習**: ユーザーの怒りだけでなく、AIのリトライパターンも検出

## Monitoring & Visibility

- **Dashboard Type**: なし（CLIツール、MCPプロトコル経由でのみアクセス）
- **Real-time Updates**: 不要（永続化されたMarkdownファイルを読み書き）
- **Key Metrics Displayed**: 検索結果件数、保存成功/失敗
- **Sharing Capabilities**: `.wasurenagusa/` ディレクトリをgit管理すればチーム共有可能
